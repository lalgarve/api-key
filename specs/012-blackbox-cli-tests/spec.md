# Spec: blackbox-cli-tests

**Status:** rascunho
**Issue:** #<a criar>

## Resumo

Uma suíte de testes de aceite em Python, escrita em BDD (cenários Gherkin), que testa a CLI
como caixa-preta: cada passo roda o jar empacotado (`java -jar api-key-<versão>.jar ...`) como
um processo separado e confere só o que um operador vê de fora — exit code, stdout e stderr. A
suíte não importa nenhuma classe Java e não lê nem escreve o banco direto.

## Motivação

Os cenários executáveis de `006-executable-gherkin-scenarios` rodam dentro da JVM de teste:
chamam os comandos pela classe Java, com o contexto Spring já montado pelo teste. Eles provam a
regra de cada comando, mas deixam de fora tudo o que só existe quando a CLI roda de verdade:

- o jar gerado por `mvn package` (manifesto, classe principal, dependências empacotadas);
- o `main` de verdade, com o exit code chegando ao sistema operacional;
- a entrada padrão real (`validate` lê a chave de stdin — `010-validate-api-key-cli` FR2);
- a separação entre stdout e stderr, que scripts usam para decidir o que fazer;
- variáveis de ambiente reais (`API_KEY_HMAC_PEPPER`, `SPRING_PROFILES_ACTIVE`,
  `SPRING_DATASOURCE_*`) e a escolha de perfil Spring na inicialização;
- o aviso de relógio simulado em stderr e o stdout intacto (`011-configurable-clock` FR7).

Um teste que passa dentro da JVM pode falhar no jar (classe principal errada, dependência fora
do pacote, exit code engolido pelo Spring). A suíte caixa-preta fecha essa lacuna testando o
artefato que vai para produção, do jeito que um operador ou script o usa.

Python foi escolhido por ser independente da stack Java: os testes não conseguem "colar" num
detalhe interno da implementação, só no contrato de linha de comando (`contracts/` de cada
spec). BDD mantém a convenção do projeto de cenários Gherkin como contrato de aceite
(`memory/constitution.md`, "Documentação viva por feature").

## Cenários (comportamento esperado)

Cenários desta suíte (a suíte testando a si mesma e o ambiente que ela monta). Os cenários de
cada comando ficam nos arquivos `.feature` da suíte, um por comando — ver FR5.

```gherkin
Feature: Black-box test harness for the CLI

  Scenario: the suite runs the packaged jar, not the classes
    Given the CLI jar was built by "mvn package"
    When I run the CLI with "list --status all"
    Then the command runs in its own process
    And the exit code is 0

  Scenario: each scenario starts from a known state
    Given a previous scenario generated keys for client "acme-<run-id>"
    When a new scenario starts
    Then no key generated by the previous scenario is visible to it

  Scenario: state is prepared only through the CLI
    Given client "acme" has an expired key
    Then that key was created by running "generate" with a past "--clock-start"
    And the database was not written by the test code

  Scenario: the plaintext key is captured from generate's stdout
    When I run the CLI with "generate --client acme"
    Then the suite stores the plaintext key printed on stdout
    And later steps can pass it to "validate" on stdin

  Scenario: a failing scenario reports what the CLI printed
    Given a scenario expects exit code 0
    When the CLI exits with code 3
    Then the failure message shows the command line, the exit code, stdout and stderr
```

Exemplos do estilo dos cenários de comando, escritos só contra o contrato de cada spec:

```gherkin
Feature: validate command (black box)

  Scenario: validate a key generated a moment ago
    Given I ran "generate --client acme" and kept the printed key
    When I run "validate" with that key on stdin
    Then the exit code is 0
    And stdout is "API key is valid for client 'acme'."
    And stderr is empty

  Scenario: validate an expired key
    Given I ran "generate --client acme --validity-days 10 --clock-start <20 days ago>" and kept the printed key
    When I run "validate" with that key on stdin
    Then the exit code is 5
    And stderr is "Invalid: the key expired."
    And stdout is empty

  Scenario: validate never echoes the key
    Given I ran "generate --client acme" and kept the printed key
    And I ran "revoke --id <its id>"
    When I run "validate" with that key on stdin
    Then the exit code is 4
    And neither stdout nor stderr contains the key

Feature: clock options (black box)

  Scenario: a simulated clock warns on stderr and keeps stdout clean
    Given I ran "generate --client acme --validity-days 30" and kept the printed key
    When I run "list --client acme --status all --clock-offset-days 31"
    Then the exit code is 0
    And stderr starts with "Warning: simulated clock in use; now is"
    And stdout is the list table with STATUS "expired"

Feature: environment (black box)

  Scenario: generate without the HMAC pepper
    Given the environment variable "API_KEY_HMAC_PEPPER" is not set
    When I run "generate --client acme"
    Then the exit code is 2
    And stderr is "Error: HMAC pepper is not configured. Set the API_KEY_HMAC_PEPPER environment variable."
    And stdout is empty
```

## Requisitos funcionais

- FR1: Nova pasta `blackbox-tests/` na raiz do repositório, fora dos módulos Maven, com o
  código Python, os arquivos `.feature` e as dependências fixadas em versão. Código,
  identificadores, nomes de arquivo e Gherkin em inglês (`memory/constitution.md`, "Idioma").
- FR2: Todo passo que executa um comando roda o jar empacotado em `api-key-cli/target/` como um
  processo filho, com argumentos, stdin e variáveis de ambiente controlados pelo passo. A suíte
  falha logo no início, com uma mensagem clara, se o jar não existir.
- FR3: As asserções usam só o que o processo devolve: exit code, stdout e stderr, separados.
  Nenhum passo importa classe Java, abre conexão com o banco ou lê arquivo interno da
  aplicação.
- FR4: O estado de que um cenário precisa (chave ativa, revogada, expirada, com revogação
  agendada, rotacionada) é montado só com comandos da própria CLI: `generate`, `revoke`,
  `--revoke-old-in-days` e as opções de relógio de `011-configurable-clock` para criar chaves
  "no passado". O `id` de uma chave sai da saída de `list`; a chave em texto puro, do stdout de
  `generate`.
- FR5: Cobertura mínima: um arquivo `.feature` por comando (`generate`, `revoke`, `list`,
  `validate`) e um para as opções de relógio, com pelo menos um cenário por exit code de cada
  contrato que seja alcançável de fora do processo (ver "Fora de escopo"), mais os cenários do
  harness acima.
- FR6: Isolamento entre cenários: cada cenário usa nomes de cliente únicos por execução, e as
  consultas com `list` sempre filtram por `--client`, para que nenhum cenário dependa do banco
  estar vazio nem veja chaves de outro cenário (mesma regra de `memory/constitution.md`,
  "Java": "nenhum teste assume a tabela vazia").
- FR7: A suíte roda contra PostgreSQL real, no mesmo banco configurado pelos perfis `sandbox`
  e `docker` (`009-remove-h2-real-postgres`), com o perfil escolhido por
  `SPRING_PROFILES_ACTIVE`. Sem Postgres de pé, os cenários falham com erro de conexão, de
  propósito.
- FR8: Quando um cenário falha, a mensagem mostra a linha de comando executada, o exit code,
  stdout e stderr completos — o suficiente para entender a falha sem rodar de novo.
- FR9: A chave em texto puro capturada de `generate` só fica em memória durante o cenário;
  nunca é gravada em arquivo nem impressa no relatório de sucesso. No relatório de falha, ela
  aparece mascarada (só o prefixo `dak_`).
- FR10: Cenários de uma feature ainda não implementada (hoje `010` e `011`) são marcados com
  uma tag (`@pending`) e não quebram a suíte enquanto a tag existir; a tag sai no mesmo PR que
  implementa a feature.
- FR11: A suíte roda no CI em toda PR, e a PR fica vermelha se algum cenário sem `@pending`
  falhar (ver "Decisões em aberto" sobre onde exatamente ela roda).
- FR12: Um único comando, documentado no `README.md`, roda a suíte localmente depois de
  `mvn package`.

## Requisitos não-funcionais

- Nenhuma mudança no código Java, no schema ou nos contratos de CLI: a suíte só consome o que
  já existe.
- Python 3.12 ou mais novo; dependências instaladas num ambiente virtual próprio da pasta, sem
  nada instalado globalmente.
- A suíte inteira roda em poucos minutos: cada processo da CLI sobe um contexto Spring, então
  os cenários preparam estado com o menor número de comandos possível.
- Nenhum segredo real: o pepper usado nos testes é um valor fixo de teste, definido pela
  própria suíte.

## Fora de escopo

- Substituir os cenários Cucumber em Java de `006` ou os testes JUnit: a suíte caixa-preta é
  uma camada a mais, não uma troca.
- Falhas que só se provocam por dentro do processo: erro de persistência (`generate` exit 3,
  `revoke` exit 4). Já estão cobertas pelos cenários de `006`.
- Os perfis `staging` e `production` de `011` FR8: eles ainda não existem como configuração;
  os cenários correspondentes entram quando existirem.
- Cobertura de código (JaCoCo) a partir da suíte Python: o piso de 80% continua medido só pela
  suíte Java.
- Testar a biblioteca `api-key-validation` dentro de um serviço protegido (HTTP).
- Rodar os cenários em paralelo.

## Decisões em aberto

- **Onde a suíte roda no build.** Duas opções:
  1. Passo próprio no CI, depois do `mvn verify`, no mesmo job (recomendado: o `mvn verify`
     continua só Java e não passa a exigir Python em todo ambiente; o CI continua com um único
     check obrigatório).
  2. Dentro do `mvn verify`, por um plugin Maven que chama o Python na fase
     `integration-test` (um só comando para tudo, como pede `006` "Requisitos
     não-funcionais", mas todo ambiente que roda `mvn verify` passa a precisar de Python).
- **Banco da suíte.** Usar o mesmo banco `deployo_api_key` dos testes Java, isolando só por
  nome de cliente (FR6, recomendado: nada novo para provisionar), ou um banco separado só para
  a suíte caixa-preta (isolamento total, mas exige criar o banco no `docker-compose.yml`, no
  CI e no script de setup do sandbox). Como a CLI não tem comando de apagar chave, na primeira
  opção as chaves criadas pela suíte ficam no banco; o sistema está em pré-produção
  (`memory/constitution.md`), então isso não protege nenhum dado real.

Decisões técnicas (framework BDD em Python, como achar o jar, como gerar nomes únicos) ficam
em `plan.md`.
